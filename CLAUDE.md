## Coding Standards

### Go Conventions

- Follow standard Go formatting (`gofmt`)
- Use meaningful variable names; avoid single-letter names except in loops
- Keep functions focused and small
- Error handling: always check and handle errors explicitly
- Use `internal/` for packages not meant for external consumption

### Error Handling

```go
if err := someOperation(); err != nil {
    return fmt.Errorf("failed to do X: %w", err)
}
```

### Naming Conventions

- Files: lowercase with underscores (`config_paths.go`)
- Packages: lowercase, single word preferred
- Public functions: PascalCase with clear verb prefixes (`CreateSymlink`, `ValidateFile`)
- Private functions: camelCase

### Design Principles

- **Safety first:** Always backup before destructive operations. Use transactions. Never leave broken state.
- **Fail gracefully:** Errors in TUI footer. Critical errors in centered modals. Git commit failures become warnings, not errors.
- **Minimal surprise:** Follow Stow/Chezmoi conventions. Keybindings follow vim/lazygit (j/k, ?, q).

## Git Workflow

### Commit Guidelines

- **Commit per feature:** Each commit covers one complete feature across all its files
- **Never combine** unrelated features in one commit
- **Clear messages:** Descriptive, present tense, imperative mood

```
# Good
feat(stow): add package discovery, link, unlink, and v1 migration
refactor(internal): simplify config, logger, and path references for stow layout

# Bad
updates
fix stuff
WIP
feat: add styles.go
```

### Prohibited Phrases

Never include in commit messages or code comments:
- "generated by Claude", "authored by Claude", "written by AI", or any AI attribution

## Development Workflow

1. Read existing code in the affected area before changing anything
2. Preserve existing style and patterns
3. Make incremental changes over large rewrites
4. **Commit after completing each feature** — not per file, not per session
5. Pre-commit gate: `go build ./... && go test ./...`
6. For architectural changes, discuss before implementing

## Building and Running

This project uses [just](https://github.com/casey/just) as its task runner. See `justfile` for all available recipes.

```bash
just build              # Build all packages
just run                # Build and run the TUI
just test               # Run all tests
just lint               # Run golangci-lint
just                    # lint + test + build (default)
just --list             # Show all recipes
```

### Linting

**IMPORTANT:** The `rtk` wrapper for golangci-lint filters/suppresses some issues.
Always run the direct binary to get accurate results:

```bash
/Users/justincordova/go/bin/golangci-lint run    # correct — shows all issues
rtk golangci-lint run                             # WRONG — misses issues
```

Do NOT commit until `/Users/justincordova/go/bin/golangci-lint run` reports 0 issues.

## Common Patterns

### Lock Acquisition

```go
func runCommand(cfg *config.Config) error {
    if err := lock.AcquireLock(cfg); err != nil {
        return err
    }
    defer lock.ReleaseLock(cfg)
}
```

### Transaction Usage

```go
tx := core.NewTransaction(cfg)
defer func() {
    if r := recover(); r != nil {
        tx.Rollback()
        panic(r)
    }
}()

if err := tx.Execute(&core.MoveFileOp{Src: src, Dst: dst, Config: cfg}); err != nil {
    return err
}
tx.Commit()
```

### Stow/Unstow

```go
packages, _ := stow.DiscoverPackages(repoDir, homeDir)
pkg := &packages[0]

result, err := stow.Link(pkg, homeDir)
result, err = stow.Unlink(pkg, homeDir)
```

### Structured Logging

```go
cfg.Logger.Debug("starting operation", "file", path)
cfg.Logger.Info("operation complete", "file", path)
```

Log output goes to `~/.dotcor/logs/dotcor.log` (not stderr — TUI owns the terminal).

## Testing Requirements

1. Reference [docs/TESTING.md](docs/TESTING.md) for conventions
2. All new features must have tests (happy path, error path, edge cases)
3. Follow AAA pattern (Arrange-Act-Assert) with testify
4. Unit tests alongside code, integration tests in `tests/`
5. Core packages target 85%+ coverage
6. TUI tests: call `Update()` with messages, assert state changes
